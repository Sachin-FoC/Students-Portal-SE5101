Authentication

How systems decide who you claim to be, and how they check whether to believe you. This lecture covers the core vocabulary of identification and authentication, how password-based login actually works under the hood, and the protocols that let authentication happen safely across a network.

  • Name and give examples of the three classic authentication factors.
  • Explain how passwords are stored safely (hashing and salting) and why plaintext storage fails.

01 Identification & Authentication

Every secure system needs to answer two separate questions before it lets you do anything: who do you say you are, and can you prove it. These are two different jobs, and conflating them is one of the most common sources of confusion, and of bugs, in security design.

STEP ONE

Identification

The act of claiming an identity. You type a username, present an ID card, or scan a badge. The system has not yet verified anything, it has just received a claim it will now try to check.

STEP TWO

Authentication

The act of proving that the claimed identity belongs to you. You supply a password, a fingerprint, or a one-time code, evidence the system can check against what it already knows about that identity.

A third, related term is worth separating out clearly too: authorization is what happens after authentication succeeds, deciding what the now-verified identity is allowed to do. A logged-in user is authenticated; whether they can delete another user's file is a question of authorization. Systems that skip this distinction tend to either over-trust a successful login or re-check identity for things that should only require a permission check.

WORKED EXAMPLE Swiping a staff card at a door is identification (the badge claims "I am employee #4021"). Being asked for a PIN afterwards is authentication (proving you're the person that badge belongs to). The door unlocking only for the server room, not the vault, is authorization.

A less common fourth category is sometimes added: something you do (behavioural biometrics, such as typing rhythm or gait) and somewhere you are (location-based signals, such as GPS or a trusted network). These are usually used to strengthen an existing factor rather than stand alone.

WHY COMBINE FACTORS A stolen password alone is not enough if the account also requires a code from a physical device, the attacker would need to compromise two independent categories of evidence, not just one. This is the entire logic behind multi-factor authentication, covered in Section 5.

03 Password Authentication

Passwords remain the most widely deployed authentication mechanism because they need no special hardware and are simple to implement. Their weaknesses come almost entirely from how they are stored and chosen, not from the concept itself.

3.1  Storing passwords safely

A naive system stores the password itself and compares it directly on login. This is dangerous: anyone who reads the database, an attacker, a careless administrator, a leaked backup, instantly obtains every user's real password. Two techniques fix this.

Hashing. Instead of the password, the server stores the output of a one-way hash function, H(password). On login, the server hashes the entered password again and compares the two hashes. A good hash function makes it computationally infeasible to reverse the process and recover the original password from its hash.

Salting. Hashing alone still has a weakness: two users with the same password produce the same hash, and attackers can pre-compute hashes for common passwords (a rainbow table) and look up matches instantly. A salt, a random value unique to each account, is combined with the password before hashing: H(password + salt). The salt is stored alongside the hash (it doesn't need to be secret) and forces an attacker to attack every account individually rather than reusing one pre-computed table.

Notice: typing the same password twice and hashing without a salt gives an identical result every time, but adding a salt changes the output even though the password didn't change. This runs entirely in your browser; nothing is sent anywhere.

SLOW HASHES, ON PURPOSE General-purpose hashes like SHA-256 are designed to be fast, which is actually bad for password storage, since it makes brute-force guessing cheap for an attacker. Real systems use deliberately slow, memory-hard functions such as bcrypt, scrypt, or Argon2, which add a configurable work factor so guessing billions of passwords becomes too expensive to be practical.

3.2  Common attacks on password systems

Click each attack below to expand its description and the standard defense against it.

HIGH

Brute-force attack

+
Systematically trying every possible character combination until the correct password is found. Feasible against short or simple passwords given enough computing time.
Defense: long minimum length, slow hash functions (bcrypt/Argon2), account lockout or rate-limiting after repeated failures.
HIGH

Dictionary attack

+
A focused brute force that only tries real words, common passwords, and known leaked passwords instead of every possible string, far faster than exhaustive search because people rarely choose truly random passwords.
Defense: block known-weak/leaked passwords at signup, encourage passphrases over dictionary words, enforce complexity that resists common patterns.
MED

Rainbow table attack

+
Using a large precomputed table mapping hashes back to plaintext passwords, so a stolen hash can be looked up almost instantly instead of recomputed.
Defense: per-account salting makes precomputed tables useless, since every account effectively needs its own table.
MED

Credential stuffing

+
Reusing username/password pairs leaked from one breached site to log into accounts on other, unrelated sites, it works because so many people reuse passwords.
Defense: unique passwords per site (password managers), multi-factor authentication, monitoring for logins matching known-breached credentials.
HIGH

Phishing

+
Tricking the user into typing their real password into a fake login page that looks legitimate, no cryptographic weakness is exploited; the human is the target.
Defense: user awareness training, phishing-resistant second factors (hardware security keys), verified sender/domain checks in email clients.
MED

Shoulder surfing & keylogging

+
Directly observing someone type their password, or capturing keystrokes with malicious software installed on their device.
Defense: masked password input fields, endpoint anti-malware protection, on-screen/virtual keyboards for high-sensitivity logins.

3.3  What good password practice looks like

✓Favour length over complexity, a long passphrase beats a short string of forced symbols.
✓Never store passwords in plaintext or with reversible encryption, only salted, slow hashes.
✓Check new passwords against known-breached password lists at signup.
✓Rate-limit and lock out repeated failed login attempts.
✓Encourage unique passwords per account, ideally via a password manager.
✓Add a second authentication factor wherever the account matters.

04 Authentication Protocols

A protocol defines the exact sequence of messages two parties exchange to authenticate, over a network, where an eavesdropper might be listening. Select a protocol below to see how it works.

The simplest possible protocol: the client sends its username and password in the clear (unencrypted) to the server, which checks them against its records and responds accept or reject.

Because the credentials travel unprotected, PAP is only ever acceptable inside an already-encrypted channel (like inside a TLS or IPsec tunnel), never over an open link. It is mostly of historical interest today, as almost everything has replaced it with something stronger.

Challenge-Handshake Auth. Protocolcredential type
Stronger than PAPsecurity level
PPP, some VPNstypical use

Instead of sending the password itself, CHAP proves knowledge of the password without ever transmitting it, using a challenge-response exchange built on a shared secret and a hash function.

  1. Server sends a challenge, a random, unpredictable value, to the client.
  2. Client computes a response, the hash of the challenge combined with the shared secret (password), and sends only that hash back.
  3. Server performs the same computation independently, using the password it has on record, and compares its result with what the client sent.
  4. Match → authenticated. Because the challenge is different every time, a captured response cannot be replayed later.

The key idea, proving knowledge of a secret without revealing it, reappears throughout security. CHAP is a simple, practical instance of this general "challenge-response" pattern.

One-Time Passwordcredential type
Strong (as 2nd factor)security level
Banking, MFA appstypical use

An OTP is a password valid for only a single login session or a short time window, generated from a shared secret so a captured code is useless afterwards. Two common variants:

  1. HOTP (HMAC-based OTP), the code is derived from the shared secret and a counter that increments every time a code is generated, on both sides.
  2. TOTP (Time-based OTP), the code is derived from the shared secret and the current time (typically rounded to a 30-second window), instead of a counter, this is what most authenticator apps use.
  3. Server independently recomputes the expected code from the same secret and counter/time, and accepts if it matches within an allowed window.

OTP is almost always combined with a password as a second factor, rather than used entirely on its own, since it only proves possession of the generating device, not identity by itself.

Ticket-based protocolcredential type
Strongsecurity level
Enterprise networks (AD)typical use

Kerberos lets a user authenticate once and then access many different services without re-entering a password for each one, using time-limited cryptographic tickets issued by a trusted third party.

  1. User → Authentication Server (AS): requests access, proving identity once (e.g. with a password-derived key).
  2. AS → User: issues a Ticket-Granting Ticket (TGT), encrypted, valid for a limited time.
  3. User → Ticket-Granting Server (TGS): presents the TGT to request access to a specific service.
  4. TGS → User: issues a service ticket for that specific service only.
  5. User → Service: presents the service ticket directly to the target service, which grants access without contacting the AS again.

The user's real password is only used once, at the very first step, and never sent to each individual service, this is what enables convenient single sign-on across many systems.

RADIUS (Remote Authentication Dial-In User Service) centralises Authentication, Authorization, and Accounting for many access points (Wi-Fi routers, VPN gateways, switches) against one shared server, rather than each device keeping its own user list.

User
→
Access point (client)
→

The access point forwards the user's credentials to the RADIUS server, which checks them centrally and returns Accept / Reject / Challenge.

This centralisation means a company can add or remove a user in one place and have that change apply instantly across every Wi-Fi access point, VPN server, and switch on the network.

Federated / delegated authcredential type
Strongsecurity level
"Sign in with…" flowstypical use

Both OAuth 2.0 and SAML let a user prove their identity to one trusted party (an identity provider) and use that proof to access other, unrelated services, without ever handing their password to those other services.

  1. User → Service Provider: tries to log in and is redirected to an Identity Provider (e.g. "Sign in with Google").
  2. User → Identity Provider: authenticates directly with the identity provider (which they already trust and have an account with).
  3. Identity Provider → Service Provider: sends back a signed proof of identity, an OAuth access token or a SAML assertion, without ever exposing the user's actual password.
  4. Service Provider: verifies the signature on the token/assertion and grants access based on it.

The practical difference: SAML is XML-based and common in enterprise single sign-on; OAuth 2.0 is token-based (often paired with OpenID Connect for identity specifically) and dominates consumer "sign in with" buttons and API access delegation.

05 Multi-Factor Authentication

Multi-factor authentication (MFA) requires evidence from two or more different factor categories from Section 2 before granting access, not just two pieces of evidence from the same category.

NOT MFA vs. MFA A password plus a security question is not true multi-factor, both are "something you know." A password plus a code from an authenticator app is multi-factor, knowledge plus possession.

MFA dramatically raises the cost of an attack, because compromising one factor (e.g. phishing a password) no longer succeeds on its own, the attacker must also compromise an entirely different category of evidence, which typically demands a different attack technique altogether.

06 Summary

Identification vs. authentication

Claiming an identity is not the same as proving it, and proving it is not the same as being authorized to act.

Three factors

Know / have / are. Strong systems combine at least two independent categories.

Never store plaintext

Passwords should be salted and hashed with a slow, memory-hard function, never reversibly encrypted.

Attacks target the weakest link

Most password attacks exploit human behaviour (reuse, weak choices, phishing) more than the cryptography itself.

Challenge-response > sending secrets

CHAP, OTP, and Kerberos all avoid transmitting the password itself across the network.

Federation enables SSO

RADIUS centralises network access decisions; OAuth2/SAML let one trusted login work across many separate services.
