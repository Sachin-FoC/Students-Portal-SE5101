Trusted Intermediaries, IPsec and IKE

How we know a key really belongs to someone (PKI and Kerberos), how IPsec protects every packet on the network (AH and ESP), and how IKE sets everything up automatically.

The big picture. Last lecture gave us strong tools: encryption, signatures, Diffie-Hellman. But they all assume one thing: you have the right key. This lesson answers three simple questions.

Part A: Who can I trust to tell me whose key is whose? (PKI, CAs, KDCs, Kerberos)

Part A

Trusted intermediaries

01

Why do we need trust?

Encryption keeps secrets. It does not tell you who you are talking to.

Alice wants to send Bob a secret, so she asks for Bob's public key. But Mallory sits in the middle of the network. She can swap Bob's key for her own. Alice encrypts with Mallory's key without knowing it, and Mallory reads everything. The maths was perfect; the key was wrong.

The idea

A trusted intermediary is a third party that everyone already trusts. It vouches for "this key belongs to this person". Examples: a Certification Authority (CA), a Registration Authority (RA), a Key Distribution Center (KDC), and the Authentication Server (AS) in Kerberos.

Three ways to trust a key

Direct trust

Alice got Bob's key from Bob himself, for example face to face. Simple, but does not scale to millions of people.

Hierarchical trust

A tree: Root CA → Intermediate CA → User. Trust the root and you can trust everything it signed. This is how HTTPS works.

Web of trust

No boss. People sign each other's keys: "I know Bob, this is his key." Used by PGP email.

02

PKI, CAs and digital certificates

A Public Key Infrastructure is the whole system that creates, hands out, checks and cancels certificates.

Think of a passport office. You show your birth certificate to a clerk (they check who you are), the office prints and stamps your passport, and border officers everywhere trust the stamp. A PKI does the same job for public keys.

Certification Authority (CA)

Issues and signs certificates. Keeps the revocation list. The "passport office". Examples: DigiCert, Let's Encrypt, GlobalSign.

Registration Authority (RA)

Checks your identity before the CA signs. The "clerk at the counter". Passes verified requests to the CA.

Certificate Repository

A public place that stores certificates and lists of cancelled (revoked) ones.

End entities

The users, servers and apps that hold and use certificates.

Chain of trust

Your browser does not know every website. It only knows a small list of root CAs built into it. The root signs an intermediate CA, and the intermediate signs the website. The browser checks each signature going up the chain until it reaches a root it already trusts.

Cancelling a certificate (revocation)

Sometimes a certificate must be cancelled before it expires: the private key was stolen, the employee left the organization, or a policy was broken. There are two ways to check if a certificate was cancelled:

CRL — Certificate Revocation List

The CA publishes a list of all cancelled serial numbers. The browser downloads it and searches it. Like checking a printed "stolen cards" list.

    OCSP — Online Certificate Status Protocol

    The browser asks the CA's server about one certificate and gets back "good" or "revoked". Like phoning the bank about one card.

      03

      Key Distribution Centers and Kerberos

      The same "trusted middle person" idea, but using only secret (symmetric) keys.

      With symmetric encryption, every pair of people needs a shared secret key. How do they get one safely? A Key Distribution Center (KDC) solves it: it shares one secret key with each user, and when Alice wants to talk to a server, the KDC creates a fresh session key and hands it safely to both.

      Kerberos in one sentence

      Kerberos is a network login protocol from MIT (Project Athena). You prove who you are once, get a "pass", and then use that pass to get tickets for each service, without ever sending your password over the network.

      Theme park analogy: at the gate you show ID and get a wristband (Ticket Granting Ticket). At each ride you show the wristband to a ticket booth and get a ride ticket (service ticket). The ride operator only checks the ticket. The KDC has two parts: the Authentication Server (AS) = the gate, and the Ticket Granting Server (TGS) = the ticket booth.

      Advantages

      • Password never sent over the network
      • Mutual authentication (both sides proven)
      • Central key management
      • Scales to large organizations, single sign-on

      Disadvantages

      • KDC is a single point of failure
      • All clocks must be in sync (tickets use timestamps)
      • Complex to set up
      • If the KDC is hacked, everything is exposed

      Part B

      IPsec: AH and ESP

      04

      What is IPsec?

      Security added at the network layer, so every IP packet can be protected.

      IP, TCP and UDP were designed when the Internet was a small, friendly network. They have no built-in security. Anyone on the path can:

      IP spoofing

      Fake the "from" address on a packet.

      Data tampering

      Change the contents on the way.

      Replay

      Record a packet and send it again later.

      Eavesdropping

      Simply read the traffic.

      Definition

      IPsec (Internet Protocol Security) is a suite of protocols that authenticates and encrypts each IP packet. It works at the network layer (Layer 3), so apps do not need to change: it is transparent to them. Defined in IETF RFCs 4301–4309.

      Five security services

      ServiceIn plain wordsStops

      IntegrityNobody changed it (checked with a hash/HMAC)Tampering
      ConfidentialityNobody can read it (encryption)Eavesdropping
      Replay protectionOld packets sent again are rejectedReplay
      Access controlOnly allowed traffic gets through (policies)Unwanted traffic

      05

      Security Associations and modes

      An agreement about how to protect packets, and two ways to wrap a packet.

      Security Association (SA)

      An SA is a one-way agreement: "packets from me to you are protected with this protocol, this algorithm and this key." Each SA has an ID number called the SPI (Security Parameter Index), which travels in every packet so the receiver knows which keys to use. Because an SA is one-way, a normal two-way conversation needs two SAs.

      Diagram: two one-way SAs

      Transport mode vs Tunnel mode

      Think of posting a letter.

      Transport mode

      Only the letter inside (payload) is protected. The original address (IP header) stays visible. Used host-to-host, e.g. a secure TCP session between two computers.

      Tunnel mode

      The whole original packet goes inside a new one with a new address. Outsiders only see gateway addresses. Used for VPNs, gateway-to-gateway.

      06

      AH and ESP

      AH = a tamper-proof seal (no secrecy). ESP = a locked box (secrecy, plus an optional seal).

      Authentication Header (AH) · protocol 51

      • Authentication + integrity, no encryption
      • Protects the payload and parts of the IP header
      • Uses an HMAC (e.g. HMAC-SHA)
      • Fields: Next Header, Payload Length, Reserved, SPI, Sequence Number, Authentication Data (ICV)

      Encapsulating Security Payload (ESP) · protocol 50

      • Encryption + integrity + authentication + anti-replay
      • The most used IPsec protocol
      • Ciphers such as AES (older: DES, 3DES)
      • Fields: SPI, Sequence Number, Payload (encrypted), Padding + Pad Length, Next Header, ICV (optional)

      Anti-replay: the sequence number

      Every AH/ESP packet carries a sequence number that goes up by one each time. The receiver remembers which numbers it has seen. If Eve records packet #2 ("pay Rs 1000") and sends it again, the receiver says "already got #2" and drops it.

      Why AH breaks with NAT

      Most home and office routers use NAT: they rewrite the source IP address of outgoing packets. AH protects the IP header, so the receiver sees a changed address and thinks the packet was tampered with. ESP does not protect the outer IP header, so it survives NAT. (In practice ESP is also wrapped in UDP port 4500 to get through NAT, called NAT-Traversal.)

      Where IPsec is used

      VPNs, secure remote access, site-to-site corporate tunnels, IPv6, protecting routing updates (OSPF, BGP).

      Performance cost

      Encryption uses CPU, extra headers add latency. Hardware crypto engines help. Always a trade-off between strength and speed.

      Pros & cons

      Pros: strong, transparent to apps, standard. Cons: complex to configure, NAT trouble (AH), overhead.

      Good to know

      IPv6: IPsec was originally a "must implement" for IPv6. Later standards (RFC 6434, RFC 8504) relaxed this to "should implement", so not every IPv6 device uses it.

      Old algorithms: MD5, DES and 3DES appear in older material but are considered weak today. Modern setups use AES (often AES-GCM) and SHA-2.

      Part C

      IPsec: IKE

      07

      IKE: Internet Key Exchange

      The "brain" that sets up IPsec. AH and ESP do the work; IKE decides the keys and the rules.

      IPsec needs keys and settings (which cipher, which hash, which key, how long it lasts) before it can protect anything. Typing these into every device by hand is slow and error-prone. IKE automates key creation, authentication and security setup.

      Two phases

      Phase 1 — build trust: the two sides agree on algorithms, run a Diffie-Hellman exchange to create a shared secret, and prove their identities. Result: a secure channel called the IKE SA.

      Phase 2 — build the tunnel: inside that secure channel, they create the IPsec SAs (cipher, keys, key lifetime) that AH/ESP will use for real data.

      Animated: IKE builds a site-to-site VPN

      How do the two sides prove who they are?

      Pre-shared key

      Both sides are configured with the same secret password. Easy, but hard to manage for many sites.

      Digital certificates

      Each side shows a certificate signed by a CA (Part A!). Best for large networks.

      Public keys

      Each side signs with its private key; the other checks with the known public key.

      What IKE gives you

      Automatic key management, mutual authentication, agreement on algorithms before any data flows, and periodic rekeying (fresh keys for long sessions).

      Where you meet it

      Site-to-site VPNs (two offices) and remote-access VPNs (a laptop to the office). Implementations: strongSwan (Linux), Cisco, Windows IPsec. (OpenVPN uses similar ideas but is TLS-based, not IKE.)

      Benefits

      • Reduces human error
      • Saves configuration time

      • Supports large networks

      Limitations

      • Configuration can be tricky
      • Older versions have compatibility issues
      • Moving to IKEv2 is recommended
      08

      Key takeaways

      Remember these
      1. Encryption is useless if you have the wrong key. Trusted intermediaries vouch for who owns which key.
      2. PKI: the RA checks identity, the CA signs a certificate (X.509) binding a name to a public key. Browsers follow the chain of trust to a root CA. Cancelled certificates are found with CRL or OCSP.
      3. Kerberos uses a KDC (AS + TGS) and symmetric keys: log in once, get a TGT, swap it for service tickets. Password never crosses the network.
      4. IPsec protects IP packets at Layer 3. An SA is one-way and identified by an SPI. Transport mode protects the payload; tunnel mode wraps the whole packet (VPNs).
      5. AH = integrity + authentication, no encryption, breaks with NAT. ESP = encryption + integrity + authentication + anti-replay, the one used in practice.
      6. IKE sets up IPsec automatically in two phases: Phase 1 builds a trusted channel (DH + authentication), Phase 2 creates the IPsec SAs. Use IKEv2.
